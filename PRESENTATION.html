Temporal Kubernetes Lab / Demo Presentation

Order events that
finish reliably.

A practical Kafka + Temporal workflow: accept an order event, process it asynchronously, and keep a durable history of what happened.

Kafka transports the event. Temporal orchestrates the work.

01 / 09
The use case

From one order event to one reliable outcome

Input

An external system sends order.created through an HTTP webhook.

Processing

Kafka buffers the event; a consumer starts OrderWorkflow.

Outcome

The Temporal Worker executes the order activity and records the result.

The demo keeps the business logic small so the event-to-workflow boundary is easy to see.

3

Consume with group temporal-order-consumer.

4

Start OrderWorkflow with ID order-{order_id}.

5

Execute process_order on hello-task-queue.

6

Commit the Kafka offset after workflow start succeeds.

04 / 09
Why both systems?

Kafka moves events.
Temporal manages work.

Kafka

Durable event log, partitions, consumer groups, buffering, replay, and decoupled producers/consumers.

Temporal

Workflow state, retries, timeouts, activity execution, idempotency, visibility, and recovery.

The integration point is deliberately simple: Kafka Consumer -> Temporal Client -> Workflow.

05 / 09
Why use it?

Benefits of Kafka + Temporal

Loose coupling

Producers do not need to know when or how workers process an order.

Resilience

Kafka buffers spikes while Temporal retries failed activities and resumes work.

Auditability

Kafka keeps the event trail; Temporal keeps the workflow history and outcome.

Scale independently

Increase Kafka consumers for ingestion or Temporal workers for execution separately.

Replay and recovery

Replay events or inspect a failed workflow without losing the original context.

Clear ownership

Kafka handles transport; Temporal handles business process state.

06 / 11
Trade-offs

Costs and limitations to plan for

More infrastructure

Kafka, Temporal, PostgreSQL, Elasticsearch, workers, and monitoring increase operational cost.

At-least-once delivery

Duplicate events can happen. Use stable Workflow IDs and idempotent Activities.

Eventual consistency

HTTP success means the event was accepted, not that the order has completed.

Debugging spans systems

Trace the event, offset, workflow ID, activity, and DLQ together with correlation IDs.

Schema evolution

Event fields need versioning and validation so old consumers keep working.

Local demo is not production

This lab uses single-node Kafka, plaintext traffic, and no production-grade HA.

The pattern pays off when workflows are long-running, failure-prone, or need a durable audit trail.

07 / 11
Reliability behavior

Three outcomes to demonstrate

Success

Valid event returns HTTP 202, starts the workflow, and completes the activity.

Rejected

Missing order_id or customer returns HTTP 400 before Kafka.

Waiting

A long-running activity leaves the workflow RUNNING until it completes.

A failed workflow is a separate Temporal path: the workflow starts, the activity errors, and history shows why.

08 / 11
Event contract

Small payload, useful identity

{
  "event_id": "evt-8f42c3",
  "event_type": "order.created",
  "occurred_at": "2026-09-09T10:30:00Z",
  "order_id": "ORD-1001",
  "customer": "Alice"
}

Idempotency

Use order-{order_id} as the Temporal Workflow ID. Duplicate Kafka delivery does not create a second workflow.

Dead letter

Malformed or incomplete events are published to order.dlq for inspection and replay.

09 / 11
Live demo

Run the happy path

# Terminal 1
kubectl -n temporal port-forward service/temporal-webhook-api 8081:8080

# Terminal 2
curl -i -X POST http://localhost:8081/webhooks/orders \
  -H 'Content-Type: application/json' \
  -d '{"order_id":"ORD-DEMO-001","customer":"Alice"}'

# Inspect the workflow
kubectl -n temporal exec deployment/temporal-admin-tools -- \
  temporal workflow describe --namespace default \
  --workflow-id order-ORD-DEMO-001

Expected: HTTP 202, then Workflow status COMPLETED.
