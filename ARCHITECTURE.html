Temporal REST API Architecture

Submit an order with HTTP. The API starts a Temporal Workflow directly; the Worker processes it from the Temporal task queue. Kafka is not used.

Architecture

REST Client
curl / HTTP
→
Webhook API
POST /webhooks/orders
→
Temporal
OrderWorkflow
→
Worker
hello-task-queue

Temporal stores workflow history in PostgreSQL and exposes visibility through Elasticsearch and Temporal UI.

Request Flow

  1. Client sends JSON containing order_id and customer.
  2. The API validates the request and starts OrderWorkflow through the Temporal Client.
  3. Workflow ID order-{order_id} identifies the order and prevents duplicate starts.
  4. Temporal queues work on hello-task-queue; the Worker runs process_order.
  5. The client inspects status and history through Temporal CLI or UI.

Test with REST

Run port-forward in one terminal:

kubectl -n temporal port-forward svc/temporal-webhook-api 8081:8080

Submit and inspect an order in another terminal:

ORDER_ID="ORD-$(date +%s)"

curl -i -X POST http://localhost:8081/webhooks/orders \
  -H 'Content-Type: application/json' \
  -d "{\"order_id\":\"${ORDER_ID}\",\"customer\":\"Alice\"}"

kubectl -n temporal exec deployment/temporal-admin-tools -- \
  temporal workflow describe --namespace default \
  --workflow-id "order-${ORDER_ID}"

Expect HTTP 202, followed by workflow status COMPLETED.

Remove Old Kafka Resources

If Kafka was previously installed in the cluster, remove the old demo resources once:

kubectl -n temporal delete deployment/order-event-consumer configmap/order-event-consumer-code \
  job/kafka-create-topics deployment/kafka service/kafka --ignore-not-found
